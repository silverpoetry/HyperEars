# 项目范围与贡献边界

HyperEars 负责第三方耳机与 HyperOS 的核心系统集成。耳机的详细配置由厂商控制 App 负责，
模块通过统一的设置跳转和运行时退避与其协作。此范围是功能与 PR 的合入条件，协议可实现、
页面可展示或测试通过，都不单独构成扩展产品范围的依据。

## 核心能力

| 范围 | 提供的能力 |
| --- | --- |
| 系统设备接入 | 正确识别候选设备，保护系统原生设备，接入已有 MiLink 流转与音量控制 |
| 电量与基础控制 | 系统整机电量回退，协议确认后的左右耳与盒电量，以及降噪、关闭、通透等核心模式 |
| 简明卡片扩展 | 已有抗风噪、游戏模式、音效档位等简明控制，按有效协议回报开放并复用统一卡片机制 |
| 原生连接展示 | 复用系统连接弹窗、超级岛和电量通知，消费同一份已接受状态 |
| 厂商 App 协作 | 按用户选择打开系统设备详情、Adapter 声明的厂商 App 或 HyperEars；按设置及作用域支持执行运行时退避 |
| 模块管理与诊断 | 作用域与会话状态、适配器选择、必要的日志和预览，以及模块自身的设置 |

简明卡片扩展须说明它服务的系统交互、能力确认依据及原生承载边界。已有个别特性不构成
新增完整控制面板的先例；可扩展的请求和状态类型也仅用于范围内、经过评审的能力。

## 详细设置交给厂商 App

以下内容由厂商 App 或系统原有功能承担，不随型号适配一并引入模块：

- 完整 EQ 编辑器、手势动作分配、语音提示参数和成套个性化设置；
- 固件检查、下载、升级及维护厂商固件服务；
- 配对管理、音频编码与 LE Audio 配置、双设备管理及音频处理；
- 眼镜的拍摄、录屏、Wi-Fi 配置和应用管理等非耳机核心控制；
- 为承载上述功能建立综合设备详情页，或新增系统设置进程 Hook、接管厂商专用详情页。

“打开系统设备详情”是导航功能，不授予模块修改系统详情页或接管其控制逻辑的职责。
厂商 App 路径使用 Adapter 的 `controlApps` 声明。运行时退避以已注入 App 的进程生命周期
为依据，不能假定 App 一定建立蓝牙连接，也不能仅凭蓝牙断开认定它已退出。
具体设置和作用域条件见[控制 App 目录](control-apps.md)。

## 系统边界

- 原生卡片、弹窗和连接提示通过已验证的语义入口接入；无法确认的入口保留标准能力并提供诊断。
  不以自绘焦点通知、手工拼接超级岛载荷或另建完整界面替代不兼容的原生路径。
- 通用 UI、导航及会话调度消费 Adapter 的声明、状态和标准事件。具体型号判断及协议差异留在
  Adapter、ProtocolSession 和专用卡片实现内，不散布到公共宿主与调度代码。
- 新传输能力只服务确有证据的端点需求，默认行为保持兼容；触发、退出、并发、失败回退及
  耗电边界随实现一同评审。匹配阶段只选候选，不建立连接或发送探测命令。
- 名称、UUID 和控制 App 属于不同证据。共享协议 UUID 可确定候选端点，不能单独确定品牌；
  控制 App 仅参与设置导航和控制权管理。
- Apple 继续由系统负责，当前匹配链保持排除；如需改变这一范围，应先另行讨论项目定位。

对象职责和实现规则见[模块架构](system-module-architecture.md)与
[贡献指南](../CONTRIBUTING.md#设计规则)。

## 提交与评审

提交前说明：

1. 对应上表哪项系统能力，以及复用的原生交互入口；
2. 型号与家族的匹配依据、只读协议确认及逐项能力开放方式；
3. 详细配置如何交给现有厂商 App，所需的控制 App 声明与退避条件；
4. 共享框架改动为何必要，如何保持其他型号的默认行为；
5. 协议来源、许可、测试与最终提交的实机复核范围。

协议适配与新的公共基础能力分别评审，避免在多个型号 PR 中重复携带整套页面、归属或调度
实现。超出本项目范围的提交会说明原因后关闭；范围内的协议事实、测试向量及适配代码可以
单独重新提交，并保留原作者署名与来源。正常维护版继续遵循贡献指南的实机复核流程。
